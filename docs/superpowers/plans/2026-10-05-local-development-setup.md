# Local Development Setup Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Provide repeatable repository-root workflows for local development and production deployment of PocketBase, SeaweedFS, and Flutter Web.

**Architecture:** Pin Task as a Go tool in a root Go module. Development keeps Flutter Web on the host and PocketBase/SeaweedFS in Compose. The production task builds Flutter Web with the host SDK, embeds the static assets into a Go image build, and serves the UI and PocketBase API from one origin. SeaweedFS remains the S3-compatible object store.

**Tech Stack:** Go 1.26.5 tool directives and `embed`, Task, Docker Compose, Flutter Web, PocketBase static routing, and SeaweedFS.

**Spec:** [`docs/superpowers/specs/2026-10-05-local-development-setup-design.md`](../specs/2026-10-05-local-development-setup-design.md)

## Global Constraints

- Start the workflow from the repository root with `go tool task dev`; do not require a globally installed Task binary.
- Keep the Flutter Web app on the host Flutter SDK at port `8080` and configure it with `BACKEND_URL=http://localhost:8090`.
- In production, build Flutter Web on the host, serve it with PocketBase from the same origin on port `8090`, default the API URL to the current page origin, and retain `BACKEND_URL` as an override.
- Do not add a separate production frontend process or container; embed the production web assets in the PocketBase Go executable.
- Use PocketBase at `http://localhost:8090`, its admin UI at `http://localhost:8090/_/`, and the OAuth callback `http://localhost:8090/api/oauth2-redirect`.
- Treat `.env` as user-owned local configuration: check that it exists without displaying, editing, creating, overwriting, or tracking it.
- Stop containers without deleting named data volumes; never use `docker compose down -v` in the workflow.
- Do not add a separate frontend container, secret seeding, or application feature changes.
- A real `OCR_API_KEY` is needed for OCR processing; launching and using flows that do not require OCR must remain possible without one.

## Repository Layout

- Create `go.mod` and generated `go.sum` at the repository root to pin Task as a Go tool independently from `backend/go.mod`.
- Create root `Taskfile.yml` with `install`, `dev`, `down`, and standalone `build` tasks.
- Add `prod` to `Taskfile.yml` and `docker-compose.prod.yml` for the production image target.
- Add `backend/web_assets.go`, an embedded `backend/web/dist/index.html` development fixture, and an embed test.
- Modify `backend/main.go` to serve embedded assets with SPA fallback; update frontend backend URL resolution to same-origin by default.
- Convert `backend/Dockerfile` to development and production targets; add root `.dockerignore` for the wider build context. The production build consumes the host-generated `frontend/build/web` directory.
- Modify `docker-compose.yml` to run the pinned SeaweedFS image, create the configured S3 bucket at startup, and start the backend only after SeaweedFS is healthy.
- Modify `backend/main.go` to pass `PB_DATA_DIR` into PocketBase startup; cover it with `backend/main_test.go`.
- Keep the previous MinIO data volume untouched; no object migration is part of this work.
- Create root `README.md` for the local quickstart, prerequisites, first-run PocketBase setup, OAuth configuration, and OCR configuration.
- Leave `.env`, `.env.example`, backend feature code, and frontend feature screens unchanged.

## Execution Notes

- SeaweedFS replaces MinIO using the pinned `chrislusf/seaweedfs:4.48` image and its S3-compatible API. The `pages` bucket exists and a signed S3 list request returned HTTP 200. No MinIO object migration is performed.
- The previous MinIO volume was absent from the final Docker volume inventory. No `docker compose down -v` or `docker volume rm` command was issued, and recent Docker event history showed no volume-destroy event; the cause is unknown, so old-volume preservation is not verified.
- PocketBase previously ignored `PB_DATA_DIR`. Startup now passes it through to `DefaultDataDir`; container verification confirmed `/pb_data/data.db` exists and remains in the named volume after shutdown.
- The production image was built from host-generated Flutter assets. Routes `/`, `/login`, `/api/health`, `/_/`, and `/main.dart.js` all responded successfully from the PocketBase container.
- `go tool task --dry build` expands to the expected Flutter build and Buildx export commands, and Buildx is installed. The Flutter build completed, but the binary export could not run because Docker Desktop reported that it was unable to start.
- A fallback `CGO_ENABLED=0 GOOS=linux GOARCH=amd64 go build` in `/tmp`, using the freshly generated Flutter assets, produced a statically linked Linux ELF. The Task's Docker Buildx export and container smoke test remain unverified until Docker Desktop can start.
- The initial Flutter-in-Docker builder was incompatible (Dart 3.12.0 versus the app's `^3.12.2` constraint); the final production task uses the host Flutter SDK before building the Go image.
- `go tool task dev` could not complete its latest smoke run because another `dartvm` process was listening on `8080`; the task's deferred Compose cleanup ran successfully.
- Flutter generated an analysis-options update during an earlier validation run; that generated edit was reverted then.
- Commit steps were intentionally not run; the work remains uncommitted.
